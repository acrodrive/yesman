- 코드의 실행 이름(`B1_seed0`, `B2_seed0`, `Bcomply_syn_seed0`, `B3_syn_seed0`, `Ours_syn_seed0`)은 바꾸지 않는다(A의 renaming 범위). 그런데 **같은 "B1"이 문서와 코드에서 다른 모델을 가리키게** 되므로, 보고서와 README의 방법 절에 이 표(문서 이름 ↔ 코드 실행 이름)를 반드시 싣는다. 혼동이 크면 실행 이름도 바꾸는 것을 다시 검토한다
- 학습 구성의 공정성: 핵심 비교는 **B3 vs Ours**이다. 그래서 **B3와 Ours는 CF 학습 구성을 각자 고른다**(B의 "CF 학습 구성 고르기"를 두 모델에 각각 적용). Ours에 맞춘 구성을 B3에 그대로 쓰면 B3가 자기에게 최적이 아닌 구성으로 학습된 셈이고, 이 불공정은 테스트로 드러나지 않는다. 이전 Ours는 따로 고르지 않고 Ours가 고른 구성을 그대로 쓴다(판단을 읽는 위치만 다르게 해서 구조 효과만 보는 ablation이므로. 초안에서는 B4도 각자 고르기로 했다가 2026-10-14에 바꿈). B1(원래 결정만)과 B2(+ CF⁺만)는 CF⁻를 쓰지 않으므로 고를 구성(질 조합, CF⁺ : CF⁻ 비율)이 없다. B2는 1단계로 늘린 CF⁺를 그대로 쓴다. 학습 step 수는 모든 모델에 같은 방식으로 다시 고른다
- 새 Ours는 아직 결과가 없다. "주 모델"로 정하는 것은 테스트 전에 하되(B의 "주 모델 선언"), 결과가 기대와 달라도 그대로 보고한다. 주장할 것은 (1) flag–경로 일치율(같은 표현에서 나오므로 높아질 것으로 기대하지만 보장되지는 않으므로 측정한 결과로 보여 준다. 이전 Ours와 비교), (2) 거부해야 할 결정을 거부하는 정도(결정 종류 안 AUC, 불가능 결정 시 안전율), (3) REJECT했을 때 그린 경로의 안전(결정을 무시한 B0가 기준점), (4) 그 대가(과잉 거부, D1 결정–경로 일치율)
- **Ours를 새 구조로 바꿔도 되는 조건**: 새 구조는 navtest(개발 세트) 결과를 보고 떠올린 것이다. 탐색에서 가설을 얻는 것은 정상이고, 확인을 처음 보는 테스트 세트에서 하면 공정하다. 대신 다음을 지킨다
  - 구조와 고르는 규칙(분기 위치, 학습 방식, 노이즈 투표, CF 학습 구성)을 **테스트 전에** step14 문서에 고정하고, 고르는 일은 검증 세트로만 한다
  - 새 모델들의 **navtest 결과는 테스트 평가가 끝난 뒤에** 본다. 먼저 보면 그 결과로 무언가를 고치고 싶어지고, 그러면 navtest를 다시 튜닝에 쓰게 된다
  - 테스트는 한 번만 돌린다. 결과를 보고 구조를 고쳐 다시 돌리면 그 테스트 세트도 개발 세트가 된다
  - 보고서에 "새 Ours의 설계는 이전 Ours의 navtest 결과 분석에서 나왔다"고 밝히고, 이전 Ours 결과도 함께 싣는다
- **Ours를 바꾼 이유 (보고서에 쓸 서사)**: 처음에는 diffusion의 랜덤성 때문에 같은 결정이 실행마다 다르게 판단되는 것을 결함으로 보고, 판단을 노이즈와 무관하게 분리했다(병렬 구조). 그 결과 판단과 경로가 서로를 보지 못해 어긋났다(판단과 행동이 다른 세상에 있었다). 경계 상황에서 판단이 흔들리는 것은 사람 운전자도 마찬가지이며(같은 상황에서도 어떤 날은 끼어들고 어떤 날은 안 끼어든다), 위험한 것은 흔들림이 아니라 판단과 행동의 불일치이다. 그래서 판단을 DiT가 경로를 만드는 내부 표현에서 읽도록 바꾸고, 랜덤성은 "흔들림이 경계 상황에 몰려 있는가"로 평가하며, 운용에서는 노이즈 여러 개로 투표해 애매하면 거부한다(B의 정할 것 ③)

    ```
    점수 = ½ × (D1 결정–경로 일치율 / B2의 D1 결정–경로 일치율)
         + ½ × (불가능 결정 시 안전율 / B0의 불가능 결정 시 안전율)
    ```
    - 한쪽만 높이는 구성(예: 다 거부해서 안전만 높음)은 다른 쪽이 깎여 점수가 낮아지므로 하한 조건이 따로 필요 없다. CF⁻를 세게 학습하면 실행 가능한 결정도 덜 따르게 되어(12단계 C에서 63.2 → 62.4%) trade-off가 생기는데, 이 점수가 그 균형을 잡는다

  - 문제: 지금 판단 head와 DiT는(B4, 현 Ours) 장면 토큰 + 결정 토큰을 각각 받아 **병렬로** 계산한다(`yesman/model.py`). 판단 head는 DiT가 경로를 만드는 과정을 보지 못하므로 둘이 따로 틀린다(head가 "따른다"고 확신했는데 경로는 안 따른 경우 32%).
  - **구조 (확정)**: DiT는 지금처럼 장면 벡터 + 결정을 받아 내부 연산 후 waypoint를 낸다. 출력이 나오기 전 적절한 위치에서 DiT 내부 표현을 **분기해 head로 열고**, flag(ACCEPT/REJECT)와 사유(충돌 / 도로 이탈 / 역주행)를 읽는다. **DiT는 한 번만 돌리고, 최종 경로는 그 DiT의 waypoint 출력이다.** REJECT일 때 그 내부 표현에는 이미 결정을 피하는 대체 경로의 표현이 들어 있어야 한다(CF⁻의 target 경로가 사람 경로이므로 DiT는 불가능한 결정을 받으면 결정을 피해 그리도록 학습된다). 판단과 경로가 같은 표현에서 나오므로 둘이 같은 맥락을 갖는다
  - flag의 뜻: ACCEPT = 이 장면에서 4초 안에 충돌·도로 이탈·역주행 없이 실행할 수 있는 결정, REJECT = 실행하면 셋 중 하나를 피할 수 없는 결정 (정답은 L2 판정)
  - 근거: 12단계 D에서 학습이 끝난 DiT의 마지막 노이즈 제거 단계 waypoint 은닉 상태(8 x 256)에 2층 MLP를 붙여 flag를 읽었더니(probe), Gemma 31B 오답 AUC가 0.67 → 0.80, 불가능 결정에서 flag–경로 일치가 68 → 76%로 올랐다. 새 Ours는 이것을 사후 probe가 아니라 모델의 정식 구조로 만든다. DiT 앞에서 판단하는 방식은 B4(현 Ours)와 같은 계열이라 후보에서 뺀다

  - 정할 것 ②: **학습 방식**. (a) DiT와 head를 함께 학습(head의 손실이 DiT 표현에도 영향) (b) DiT를 먼저 학습하고 고정한 뒤 head만 학습(12단계 D와 같음). (a)는 판단에 필요한 정보가 표현에 더 담길 수 있지만 경로 품질에 영향을 줄 수 있다
  - 기대와 한계: flag–경로 일치는 직렬로 강제한 것이 아니므로 **보장되지 않는다**. 같은 표현을 공유해 높아질 것으로 기대하는 값이고, 그래서 이 일치율 자체가 측정해서 보여 줄 결과가 된다. REJECT인데 경로가 결정을 반쯤 따르는 결정 누설도 구조적으로 막지는 못한다. 안전은 결국 **거부해야 할 결정을 거부하느냐**(판단 정확도)와 **REJECT일 때 DiT가 결정을 피해 그리느냐**에 달렸고, 이것은 CF 학습 구성으로 올린다. ACCEPT인데 DiT가 결정을 따르지 못하는 경우(약 27%)도 남는다
  - 정할 것 ③: **시작 노이즈 여러 개로 판단하기 (투표)**. 판단이 DiT 내부에서 나오므로 노이즈에 따라 달라질 수 있다. 같은 입력에 노이즈 K개로 DiT를 돌리고(한 배치), REJECT가 m개 이상이면 거부한다(예: K = 10, m = 3). 최종 경로는 **최종 판단과 같은 flag를 낸 샘플 중에서** 고른다(거부면 REJECT를 낸 샘플의 경로, 아니면 ACCEPT를 낸 샘플의 경로). 그러면 출력 단계에서 판단과 경로가 맞는다. 노이즈마다 판단이 다를 수 있는 것을 결함으로 보지 않는다. 사람도 경계 상황에서는 날마다 판단이 다르고, 위험한 것은 흔들림이 아니라 판단과 행동의 불일치이다
    - m은 직관으로 정하지 않고 검증 세트로 고른다. 후보 예: m = 1 / 2 / 3 / 5 (K = 10). 규칙 예: 실행 가능한 결정을 거부하는 비율이 5% 이하인 m 중 불가능 결정 시 안전율이 가장 높은 것 (지금 τ를 정한 방식과 같음). REJECT 개수 / K는 거부 확률의 추정값이므로 m을 고르는 것은 τ를 고르는 것과 같다
    - 확인할 것: (a) K개가 모두 ACCEPT인 결정이 실제로 L2에서 가능한가(확신하면서 틀리는 경우 찾기) (b) 판단이 흔들리는 결정이 L2 통과 후보 비율(`n_pass / n_scored`)이 낮은 경계 상황에 몰려 있나 (c) K별 추론 지연(E의 지연 측정에 K = 1, 5, 10 추가)
  - ①, ②, ③을 검증 세트로 고르는 규칙을 이 문서에 적는다

- [ ] **L2 구조 변경 (step14와 분리)**: 사람 경로를 빌려 오지 않고 결정에서 경로를 직접 만들어 판정한다. 사람이 안 해 본 결정도 판정할 수 있으므로 CF 다양성의 근본 해결책이다. L2를 바꾸면 CF⁺/CF⁻ 라벨이 바뀌어 D1, D2, 학습 묶음이 모두 달라지므로 **step14는 기존 L2로 진행**한다
  - **지금 할 것: 가능성 확인만.** 기존 L2는 그대로 두고 `yesman/l2_gen.py`(가칭)를 따로 만든다. 결정 → `yesman/synth.py`의 `candidates`로 경로 변형 생성 → `synth.matching`(L1 재판정) → `scoring.BatchScorer` 시뮬레이션 → 하나라도 통과하면 가능. 사람 경로와 많이 다른 결정(예: 사람은 섰는데 go 1.0)을 위해 사람 경로 없이 차로와 현재 속도만으로 만드는 생성 방식도 둔다
  - 가능성 확인 기준: ① 사람의 원래 결정이 거의 다 "가능"인가(기존 L2 99.3%) ② 둘 다 판정할 수 있는 결정에서 기존 L2와 얼마나 일치하나, 불일치는 그림으로 확인 ③ 생성기가 사람 경로 200개보다 덜 다양해서 할 수 있는 결정을 "불가능"으로 판정하지 않나(가장 큰 위험) ④ 판정 불가 비율이 얼마나 줄어드나(기존 CF 판정의 약 45%)
  - 모델 학습에는 쓰지 않으므로 검증 세트나 navtest에서 해도 step14의 공정성에 영향이 없다
  - **실제로 도입하는 조건**: step14 결과가 예상처럼 나오지 않아, 그 원인이 CF의 다양성(규칙 기반·plausible CF로 만들 수 없는 결정) 쪽으로 보일 때만 한다. 이때 step14의 테스트 세트는 결과를 본 셈이 되므로, 도입 후의 확인에는 또 다른 처음 보는 데이터가 필요하다(남은 navtrain 카메라 조각 16개)
