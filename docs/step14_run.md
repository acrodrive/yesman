### 결론 (탐색)

- 주된 원인은 확장·plausible CF가 채운 **CF⁻의 바뀐 종류**(앞뒤 행동, 강도, 여러 가지를 함께 바꾼 결정)이다. 메뉴 CF⁻는 13단계와 14단계 모두 약 90%가 좌우만 바꾼 결정이고, D3x의 실행 불가능한 결정 415개에는 좌우만 바꾼 결정이 하나도 없다.
- 안전율은 종류의 개수가 아니라 **CF⁻ 무게 중 좌우만 바꾸지 않은 결정의 비율**을 따라간다(학습 코드의 무게 규칙으로 계산: 13단계 10.1%, 메뉴만 10.7%, plausible 뺌 26.9%, 확장 뺌 64.0%, 기준 70.5%). 메뉴만 쓴 모델에도 새 종류 CF⁻가 4,320개(13단계 472개의 9배) 있지만 비율이 13단계와 같고 안전율도 +4.3%p뿐이다. plausible을 뺄 때만 떨어지는 것(−4.6%p)도 plausible이 CF⁻ 무게의 60%를 받기 때문에 비율이 크게 줄어서이다. 확장과 plausible이 대칭으로 서로 대신하는 것은 아니다.
- CF⁻의 개수, batch 구성, 그럴싸함 강조(plausible 비중, 확장 CF의 낮은 그럴싸함 점수로도 같은 효과)는 원인으로 보이지 않는다. 메뉴 + 확장(54.9%)과 메뉴만(42.4%)의 차이 12.5%p는 구간을 아직 계산하지 않았다.
- 비율 때문인지 확장·plausible CF⁻의 내용 때문인지는 아직 가르지 못했다. 메뉴만 쓰되 좌우만 바꾸지 않은 CF⁻의 무게를 약 70%로 올린 B3로 가를 수 있다.
- D2(메뉴 CF⁻)에서는 메뉴만 쓴 모델이 가장 높다. 규칙 기반 평가와 검증 세트로는 이 효과가 보이지 않는다.
- 대략적인 나눔(+25.8%p): 새 종류 CF⁻ 약 15%p, 그 밖의 데이터·학습 변화 약 7%p, 최종 구성 약 4%p.
- 한계: 시드 하나, B3 중심, 바뀐 것별 결정 수가 작다(18~200), navtest는 개발 세트이다.

- 이전 Ours(판단 head가 DiT와 병렬, 코드 `Ours_s14_pl04_r1`)는 Ours의 구성(plausible 0.4, CF⁻ 무게 1)으로 학습했다. 검증 결정 종류 안 AUC 0.8675.

| 학습·평가 순서 | 차례로 | 학습(GPU)은 하나씩, 평가(CPU)는 다음 학습과 겹쳐 (최대 2개) | 시간. 결과는 같다 |

### 해석해서 정한 것 (사전 등록에 구체적으로 없던 것)

- **"2단계 이전의 기본 구성"(4.1절 장면 수 단계, 4.2절 step 수·크기)**: CF⁻ 무게 0.25(13단계 값), **plausible CF⁻ 비중 0.6**, 강도 기준 무게·결정 종류별 균형·plausibility 가중치는 끔. `scripts/run_step14_train.sh`의 `BASE4`. 처음에는 비중을 묶음 그대로(CF⁻의 6.1%, plausible CF⁻ 5,743개)로 두었으나, 진짜 학습 전에 사용자와 0.6으로 바꿨다(2026-10-16, 결과를 보기 전). 이유: step 수는 모든 모델에 같게 쓰는데, 최종 모델은 2단계에서 0.4/0.6/0.85 중 하나를 써서 plausible CF⁻ 한 행을 규칙 기반보다 10/23/88배 자주 본다. 6%로 고른 step 수는 그런 반복을 반영하지 못해 과적합 쪽으로 길게 고를 수 있다. 0.6은 세 후보의 가운데라 어느 후보가 뽑혀도 차이가 가장 작다.
- **노이즈 투표 m을 고르지 못할 때 (5.2절)**: 사전 등록은 "과잉 거부 5% 이하인 m(1/2/3/5) 중 안전율이 가장 높은 것"만 정했고, 그런 m이 없을 때는 정하지 않았다. 흐름 확인 모델(200 step)에서 실제로 그랬다(m = 1/2/3/5의 과잉 거부 8.4/7.9/7.2/6.1%, 노이즈 1개 5.0%). τ는 노이즈 1개 기준이라, 노이즈마다 판단이 흔들리면 투표에서 거부가 늘 수 있다. 사용자 결정(2026-10-16, 진짜 결과를 보기 전): **그런 m이 없으면 고르지 않고, m = 1/2/3/5의 검증 결과 표만 보고한다. 테스트 평가에서 투표는 뺀다.** 5% 기준과 m 후보는 바꾸지 않는다. 투표는 가설 없이 보고만 하는 분석이라 주 결과에는 영향이 없다.
- **학습 장면에서 빠지는 장면**: 원래 결정이 판정 불가인 장면(약 3%)은 CF를 만들지 않으므로 학습 묶음에서 빠진다(이전 단계와 같은 규칙).

## 사고 기록

- **10-15 03:12~03:44, 메모리 한도 초과로 VLM 엔진이 죽음**: plausible CF 판정을 메뉴·확장 CF와 동시에 띄웠다. 닮은 장면 찾기가 GPU를 써서 처음에는 GPU 메모리 부족으로 실패했고(GPU는 VLM이 사용 중), CPU로 바꿔 다시 띄우자 컨테이너 메모리 한도를 넘었다. **이 컨테이너의 메모리 한도는 60 GB**(cgroup `memory.max`)이고, `free`의 123 GB는 호스트 값이다. 강제 종료가 VLM 엔진도 함께 죽였다.
  - VLM은 1,000장면마다 저장하므로 7,000장면까지 남았다(약 700장면 다시 함). 데이터 스크립트가 불완전한 결과로 T3를 만들기 전에 VLM 단계를 멈췄고(T3는 만들어지지 않음), 저장된 곳부터 다시 시작했다. VLM 결정은 greedy 디코딩이라 다시 해도 같다.
  - plausible CF는 확장 CF와 VLM이 끝난 뒤 GPU로 다시 돌린다. 이후 동시 작업은 메모리 60 GB 안에서 잡는다.

- **CPU 한도 13.6코어**: 컨테이너의 CPU 한도(cgroup `cpu.max`)는 13.6코어이다(`nproc`은 32, `top`의 놀고 있는 CPU도 호스트 기준). 데이터 준비는 CPU 계산량이 시간을 정한다. 판정을 동시에 돌려도 전체 시간은 줄지 않는다. 처음에 "디스크 읽기 대기"라고 본 것은 잘못이었다(io·memory pressure 0, cpu pressure 76%).

## 고친 버그 (실행 전에 발견)

- **판단 기준값 τ 파일 이름 (10-16, 흐름 확인에서 발견)**: `flag_threshold.py --val_only`는 τ를 `flag_threshold_val.json`에 쓰는데, 고르기와 평가는 `flag_threshold.json`을 읽는다. 그래서 Ours 후보를 고를 때 판단을 무시하고 항상 ACCEPT로 세었다(과잉 거부가 점수에 반영되지 않음). 오류 없이 지나가서, 흐름 확인의 투표 단계에서 파일이 없어 멈추고서야 드러났다. 진짜 학습 전이라 결과에 영향은 없다. τ를 두 이름으로 저장하고, 고르기는 판단 모델에 τ가 없으면 멈추게 했다.
- **묶음 순서 (10-16)**: 원래 결정 행이 없는 장면의 plausible 행을 target 경로를 정하기 전에 빼지 않아 멈췄다(위 묶음 설명). 결과는 의도와 같다.

- **metric cache 목록 덮어쓰기**: 학습 추가 장면의 cache를 기존 `navtrain_sensor` 폴더에 만들면, caching이 목록(metadata csv)을 새 장면만으로 덮어써 기존 2.3만 장면이 목록에서 빠진다(`MetricCacheLoader`는 첫 csv만 읽는다). 학습 추가 장면은 따로 만들고, 두 목록을 합친 `navtrain_step14_train`(목록만 있음)으로 읽는다. `l3_synth.py`에 `--cache`를 추가했고, 검증 세트(`val`)의 cache도 이 목록을 쓴다(`yesman/eval_sets.py`).
- 단계별 스크립트는 맥에서 썼고 pod에서 처음 돌았다. 데이터 준비 전에 모든 단계를 기존 장면 몇 개로 돌려 보았다(`logs/step14/overnight_notes.md`).
